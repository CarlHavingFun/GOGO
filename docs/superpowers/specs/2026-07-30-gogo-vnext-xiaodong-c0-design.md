## 1. 目标与边界

本规格同时解决三个问题：

1. 把 ImageGen 生成物视为有版本、有判断记录的 Markdown 设计过程，而不是直接可入库的最终素材；
2. 以用户提供的参考图为“小洞大人”职业选手角色的第一视觉依据，先建立 C0 视觉母版和动作关键姿势；
3. 统一现有里程碑、素材阶段、数据所有权、内容 ID 与验收门槛，使后续计划可以逐关验证。

本轮通过规格后实施的内容：

- 修订设计文档中的里程碑与 R2 政策；
- 扩充素材 manifest 结构和“小洞大人”资产清单；
- 建立“小洞大人”Markdown 设计卡；
- 用 ImageGen 生成 C0 视觉母版和动作关键姿势；
- 对生成物做参考一致性、动画可行性和项目风格 QA；
- 保留清晰的接受、返工和拒绝记录。

本轮不做：

- 不把 C0 图宣称为 A5 正式 Sprite Sheet；
- 不把 AI 原图未经清理直接导入 Godot；
- 不制作真实战队 Logo、赞助商标记、官方赛事视觉或官方 UI；
- 不提前批量生成其他 A4/A5 正式资产；
- 不修改当前 M0 战斗实现。

## 2. R2 职业选手角色参考政策

### 2.1 适用对象

R2 只适用于有用户指定参考图的职业选手角色。非职业选手角色、敌人、Boss、武器、投掷物、场景、特效与 UI 继续采用原创设计。

### 2.2 优先级

职业选手角色发生视觉冲突时，按以下顺序裁决：

1. 用户明确选择和当前角色参考图；
2. 本规格登记的身份锚点；
3. GOGO 统一视角、逻辑画布、轮廓、色板、锚点与动画技术要求；
4. 旧角色文字描述与旧 Prompt。

参考图决定人物的可识别神似和主要身份特征；项目规范只负责把人物转译成统一的游戏视角与像素动画语言。不得用“项目风格化”为理由擅自替换参考图中的核心发型、身形、服装色块和气质。

### 2.3 可保留与必须去除

允许保留：

- 可识别的脸部整体关系和气质；
- 发型、发色、身形比例；
- 无品牌的日常服装轮廓和主要色块；
- 参考图所表达的年龄感与站姿气质。

必须去除：

- 真实战队队标；
- 赞助商、平台和赛事 Logo；
- 官方队服上的受保护图案；
- 官方赛事 UI、奖杯、舞台、摄影背景和水印；
- 未经单独确认的第三方道具或角色资产。

若参考图本身没有上述元素，不新增类似元素来强化职业身份。

### 2.4 来源记录

正式设计卡记录参考图文件名、尺寸、哈希、用途与 R2 决策。临时附件路径不能成为长期唯一来源；进入实施后将保存一份仅供内部设计追溯的稳定参考副本，并在设计卡中记录相对路径。生成图不得反向被标记为“原始参考图”。

## 3. “小洞大人”视觉定义

### 3.1 身份锚点

参考图优先锁定以下特征：

- 棕色、齐下颌附近的中短发，近似自然中分，发尾形成清晰的两侧轮廓；
- 偏瘦、四肢修长但在 Q 版中仍保持紧凑；
- 宽松纯黑短袖上衣、黑色长裤、黑色鞋；
- 冷静、克制、略显疏离的表情；
- 自然站立，不采用夸张冲锋、前倾攻击或战术队服姿态。

旧 Prompt 中“凌乱深色短发、红橙点缀、紧凑运动体型、强烈前倾、黑色战术服”的冲突部分全部失效。

### 3.2 项目转译

- 表现：紧凑 Q 版像素游戏角色；
- 视角：俯视 3/4；
- 默认朝向：右下；
- 构图：完整全身，双脚清晰，主体占画布约 72%～82%；
- 逻辑画布：角色帧 128×128，头像 128×128；
- 轮廓：1～2 个逻辑像素的深色外轮廓；
- 光照：左上方；
- 色板：棕发、暖肤色、黑/深灰服装，不额外添加角色强调色；
- 锚点：每帧双脚中点或身体底部中心保持一致；
- 武器：始终作为独立节点和独立资产，不画进角色主体；
- 方向：先制作右下朝向，水平翻转覆盖左下朝向；只有玩法验证证明读向不足时才增加独立方向。

### 3.3 动作语义

角色的“高速突破手”身份主要通过动画节奏和技能反馈表达，而不是改变参考图服装或静态气质。

- `idle`：轻微呼吸和重心变化，克制，不做挑衅动作；
- `walk`：快速、短促、稳定，发尾和上衣下摆有小幅次级运动；
- `hit`：短促受击后立即回正，不血腥；
- `death`：失衡倒下或像素化退场，不出现肢解和血浆；
- `skill_breakin`（破门）：先压低重心，再短距爆发，最后回稳；空手主体不含武器、火焰或文字特效。

## 5. ImageGen 分阶段母版法

### 5.1 为什么不用一次生成最终 Sprite Sheet

一次生成整张 Sprite Sheet 容易造成脸、发型、服装、肢体数量、透视与脚底锚点逐帧漂移。生产顺序改为：

```text
参考图与 R2 规则
      ↓
视觉母版
      ↓ 用户/设计 QA 通过
动作关键姿势
      ↓ 一致性 QA 通过
轮廓、色板、透明边缘与锚点清理
      ↓
人工补间和 Sprite Sheet 组装
      ↓
Godot 实机验收
```

### 5.2 生成轮次

第一轮只生成视觉母版。母版未通过时，不继续生成动作。

第二轮以已通过概念审查的母版和原始参考图共同约束头像与动作关键姿势。每个动作单独生成，禁止把武器、文字、UI、场景或技能特效混进身体图。

第三轮只针对已识别的问题返工，例如发型不一致、服装出现 Logo、视角偏正面、脚底不完整或额外肢体。不得用无目标的反复抽卡替代问题诊断。

### 5.3 Prompt 规则

正向 Prompt 必须明确：

- 同一角色、同一棕色齐下颌中短发、同一偏瘦体型；
- 宽松纯黑短袖、黑色长裤、黑鞋；
- 冷静克制表情；
- 俯视 3/4、右下朝向、全身、空手；
- 紧凑 Q 版像素游戏资产、清晰像素簇、有限色板、左上光；
- 透明背景、无地面、无投影。

排除项必须包含：

- 无队标、无赞助商、无赛事 Logo、无水印、无文字；
- 无武器、无手榴弹、无 UI、无场景；
- 无战术背心、无红橙强调色、无夸张冲锋姿态；
- 无额外手脚、无缺失肢体、无模糊抗锯齿边缘；
- 无写实照片、无 3D 渲染、无矢量插画；
- 不改变发长、发色、服装主色或体型。

### 5.4 文件组织

实施后的稳定结构：

```text
assets/
├── characters/xiaodong/
│   └── character_xiaodong_design.md
├── source/
│   ├── references/characters/xiaodong/
│   │   └── reference_01.jpg
│   ├── generated/c0/xiaodong/
│   │   ├── master/
│   │   ├── portrait/
│   │   └── keyposes/
│   ├── cleaned/c0/xiaodong/
│   └── rejected/c0/xiaodong/
└── ui/portraits/
```

生成工具的临时路径不写入游戏资源引用。进入 A5 的稳定文件不带日期和候选版本号；源图、候选图与拒绝图保留版本号。

## 6. ImageGen 生成物作为 Markdown 设计

`assets/characters/xiaodong/character_xiaodong_design.md` 是该角色视觉决策的权威入口。每次生成后追加一条候选记录，至少包含：

- 候选 ID、生成时间、生成工具与源文件相对路径；
- 使用的参考图 ID 和 SHA-256；
- 完整正向 Prompt 与排除项；
- 目标动作、视角、逻辑画布、方向、帧用途；
- 保留的身份锚点；
- 与参考图的差异；
- 技术 QA：透明背景、肢体、轮廓、色板、脚底、锚点；
- 设计 QA：神似、气质、服装、动作语义、战斗可读性；
- 决定：`accepted_for_concept`、`revise` 或 `rejected`；
- 决定理由、下一轮只允许修改的项目；
- 关联的清理结果和最终 manifest 条目。

PNG 是证据和素材候选；Markdown 记录它为什么被接受或拒绝。只有 Markdown 决策、manifest 状态与文件实际位置一致时，素材状态才允许向后流转。

## 7. 素材状态与 manifest

统一状态流：

```text
planned → generated → cleaned → approved → in_game
                  ↘ rejected
```

C0 设计卡可使用 `accepted_for_concept` 表示母版或关键姿势通过概念审查；该值不替代正式 manifest 状态，也不允许直接进入游戏。

现有 manifest 的 13 列不足以支撑现有规范。实施时保留已有信息，并补足：

- `generation_canvas`
- `direction`
- `collision_reference`
- `palette`
- `negative_constraints`
- `godot_import`
- `reviewer`
- `reference_source`
- `reference_sha256`
- `reference_rights_policy`
- `sprite_layout`

校验器必须确认状态与文件存在性一致。例如 `generated` 必须有源输出和 Prompt 记录，`cleaned` 必须有清理结果，`approved` 必须有 QA 结论，`in_game` 必须有 Godot 验收证据。

## 8. 统一产品路线

里程碑采用以下唯一含义：

| 阶段 | 交付与出口条件 |
|---|---|
| G0 设计治理 | 文档编号统一；R2、ID、状态所有权、manifest 与校验规则落地 |
| M0 射击玩具 | 当前 AK 射击、换弹、命中、移动；自动测试通过且 Windows 手工清单通过 |
| M1 五波闭环 | 3 种敌人、赏金、升级、商店、5 波、重开、最小遥测 |
| M2 角色与战术 | 尼尼+Deagle+背身机制；大表哥+烟雾；组合验证 |
| M3 十波垂直切片 | 3 枪、4 投掷物、8 敌人、小 Boss、20～25 个升级子集 |
| M4 二十波 Alpha | 5 角色、5 枪、完整 20 波、Boss、剩余内容和 A5 正式素材 |
| M5 平衡与 Windows 发布 | 性能、平衡、可用性、Windows 打包；Beta/RC/1.0 作为子门 |
| 1.0 后 | 根据数据决定其他平台与扩展内容 |

M0 自动工程验收已通过，但手工清单尚未勾选，因此 M0 不视为完整出门。M1 内部拆成：

- M1A：3 种敌人和 3 波战斗；
- M1B：赏金、升级、商店和 5 波闭环；
- M1C：重开、遥测和复现测试。

实施注记（2026-07-30）：以上“M0 手工清单尚未勾选”保留为本规格获批时的历史快照。用户随后报告 Windows 验收完成；G0 只记录该后续报告，不把当前缺失的三名测试者报告、硬件、build 和 Review 元数据推定为已存在，也不据此补写验收证据。

实施允许对 TDD 顺序作如下细化，但不改变本规格的交付顺序：Validator kernel 可以先针对合成 fixture 开发；只有实施步骤 1～5 的文档、正式 manifest、稳定参考和设计卡全部落地后，才运行生产 G0 门；C0 生成仍严格在生产 G0 门通过之后。

## 10. 关键玩法修订

以下修订进入后续文档实施：

1. 单局时长按现有 20 波计算先采用中位数 30～35 分钟、P90 不超过 40 分钟，待实测后收窄；
2. 完整一局免费升级控制在 20～24 次，避免 47 个现有升级与商店、Boss 奖励共同导致流派收敛；
3. 波次结算顺序统一为：资源 → 波末事件 → 利息 → 固定奖励节点 → 清空待选升级 → 生成并打开商店；
4. 小洞大人解锁改为任意角色可完成的通用挑战“4 秒内击杀 8 名敌人”；开发期 5 名角色全开；
5. 烟雾在测试期默认可用，大表哥正式解锁条件不得依赖尚未解锁的自身能力；
6. 从第 3 波开始低频生成通用背身和诱饵机会，专属敌人在第 8/13 波强化，而不是首次让角色被动有意义；
7. 小洞大人的 6 秒焦躁计时只在存在可达有效目标时运行，开波有 3 秒宽限；
8. 设备在非 AWP 状态获得通用稳定性/后坐控制收益，并拥有不依赖 AWP 的收集来源；
9. 火焰对维修节点降低治疗效率但不无限打断，对护盾提供部分穿透或折减；HE 仍是主要破盾手段；
10. P0 同时可见危险总上限普通战 6、Boss 战 7；同类边缘箭头合并，小伤害数字默认聚合。

## 11. 数据所有权与内容 ID

### 11.1 状态所有权

- `RunConfig` 只读：seed、难度、角色、武器、起始投掷物；
- `RunState`：阶段、波次、时间、RNG 流、事件序号与各子状态引用；
- `EconomyState`：钱包、经验、等级、待选升级数量；
- `UpgradeState`：升级、契约和叠层。

同一可变数据不得在两个状态对象中重复拥有。

### 11.2 武器数据

第二把武器进入实现前，`WeaponDef` 统一设计文档与代码字段，至少包含稳定 `id`、tags、damage、reload、range、pierce 与 weakpoint 语义。禁止同时保留 `base_damage/damage`、`reload_sec/reload_duration`、`max_range_px/range_pixels` 两套名称而无转换层。

### 11.3 ID

玩法 ID 使用小写命名空间：

- `char_xiaodong`
- `wpn_ak`
- `throw_smoke`
- `enemy_chaser`
- `upgrade_don_01`

素材 ID 独立表达文件职责，如 `character_xiaodong_idle`。显示名独立本地化，不用中文显示名充当稳定 ID。

## 12. 验证与样本门槛

### 12.1 自动校验

M1 前增加最小 `ContentValidator`，检查：

- 所有玩法 ID 唯一且引用存在；
- 武器数值范围和必填字段；
- 47 个现有升级的分类、引用与互斥关系；
- 每名角色恰有 3 个模块；
- 每把武器至少有 1 个突变；
- 波次数据恰好覆盖 1～20；
- 解锁依赖图无环；
- manifest 必填字段、状态流与文件存在性；
- 每个生成资产都有 Prompt 和排除项；
- 设计文档 manifest 的文件列表和哈希与实际一致。

### 12.2 玩法样本

## 13. 错误、返工与拒绝

- 身份锚点错误：回到视觉母版，不继续动作；
- 单一动作错误：只返工该动作，不重抽已通过母版；
- 出现 Logo/文字/第三方标记：直接拒绝，不靠裁切掩盖；
- 多肢、缺肢、手脚粘连：拒绝或定向局部返工；
- 背景不透明或有脏边：可进入清理，但不得标记 `approved`；
- 风格可用但神似不足：标记 `revise`，明确只修改发型/脸部关系等身份项；
- 神似正确但动作读不清：保留为母版证据，动作单独返工；
- 连续两轮出现同类错误：调整 Prompt、参考输入或拆分任务，不继续无目标生成。

拒绝图移入 `assets/source/rejected/c0/xiaodong/`，设计卡保留原因；不得删除记录来制造“全部通过”的假象。
