## 2. 双轨推进原则

### 2.1 玩法轨道

当前先完成 M1 灰盒战斗玩具的自动与人工验收；全部强制门槛通过后，Codex 才能把阶段改为 M2，并开始 M2 的第一个单闭环工作包。

### 2.2 美术轨道

M0/A0 只建立可重复的角色素材管线并批准角色母版，不把全部正式动画直接塞进当前灰盒场景。

固定顺序：

1. 登记并保存小洞大人参考图；
2. 生成并审批小洞大人标准立姿；
3. 生成尼尼、设备、上帝、大表哥标准立姿；
4. 进行五人 `CharacterLineupReview`；
5. 五人标准立姿全部通过后，优先生产小洞大人完整 M0 动画；
6. 使用 Godot MCP 导入 `AssetGallery` 验收；
7. 只有通过透明边缘、锚点、帧间一致性和实机场景检查的文件才能标记 `in_game`。

在第 4 步通过前，禁止生成小洞大人的动作帧、头像或换装。

## 3. 小洞大人参考图

仓库参考路径：

```text
assets/characters/xiaodong/reference/xiaodong_approved_pixel_anchor_v01.jpeg
```

用途：

- 作为已批准的外形与像素表现锚点；
- 锁定棕黑色中长发、自然中分、偏瘦长脸、窄肩和黑色简洁服装；
- 帮助后续帧保持同一角色，而不是每帧重新设计人物。

限制：

- 该图是白底高分辨率参考，不是运行时 Sprite；
- 不直接导入游戏场景；
- 不从图中复制真实队服、队标、赞助商或赛事元素；
- 正式 Sprite 必须转译为 128×128 逻辑画布、透明背景、俯视 3/4、朝右下、左上光和项目色板。

## 4. 标准生产母帧

### 4.1 Asset ID

```text
character_xiaodong_standard_pose
```

### 4.2 目标路径

```text
assets/characters/xiaodong/standard/character_xiaodong_standard_pose_v01.png
```

### 4.3 硬性要求

- 128×128 逻辑画布；
- 全身、空手、透明背景；
- 俯视 3/4，默认朝右下；
- 双脚中点为 `feet_center`；
- 左上光；
- 1～2 个逻辑像素外轮廓；
- 不能使用真实队服、队标、赞助商、文字或武器；
- 发型必须保留自然中分和到耳朵/下颌附近的中长轮廓；
- 体型保持窄肩、瘦长、四肢偏细；
- 后续全部动画从该母帧修改，不重新随机生成人物。

### 4.4 审批门槛

必须在 100% 与游戏实际放大倍率下同时检查：

- 发型、脸型、肩宽和腿长是否稳定；
- 身体方向是否能一眼辨认；
- 双脚锚点是否明确；
- 透明边缘是否无白边、灰边和半透明脏像素；
- 镜像后是否仍可用；
- 与另外四名角色放在同一 `CharacterLineupReview` 中是否属于同一世界。

## 5. 小洞大人 M0 动画包

原 23 帧草案需要按当前 Style Bible 修正：移动由 6 帧统一为 8 帧；M0 需要补充 Ctrl 蹲姿；投掷动作属于 M2 投掷物闭环，先登记但不在 M0 生产。

### 5.1 M0 必做帧

| 动画 | 帧数 | FPS | 循环 | 说明 |
|---|---:|---:|---|---|
| `idle` | 4 | 6 | 是 | 呼吸与发尾轻微摆动，幅度 1～2 逻辑像素 |
| `walk` | 8 | 10 | 是 | 双腿完整交替，发型有轻微惯性，脚底不漂移 |
| `crouch_idle` | 4 | 6 | 是 | 对应 Ctrl 降后坐力状态，碰撞与脚底锚点不改变 |
| `crouch_walk` | 8 | 8 | 是 | 低姿移动，不能缩成矮胖比例 |
| `hit` | 2 | 12 | 否 | 上半身收缩，击退距离由引擎控制 |
| `death` | 6 | 10 | 否 | 非血腥侧前方倒地，最后一帧保持 |

合计 32 张独立动作帧。标准母帧可复用为 `idle_00`，因此仓库中小洞大人 M0 角色本体为 **32 张唯一 PNG**；按动画序列计数为 33 帧槽位。

### 5.2 M2 预登记帧

| 动画 | 帧数 | FPS | 触发阶段 |
|---|---:|---:|---|
| `throw` | 5 | 10 | M2 手雷/烟雾闭环 |

角色帧中不画手雷。投掷物作为独立节点绑定 `ThrowablePoint`，在释放帧脱离手部。

### 5.3 文件结构

```text
assets/characters/xiaodong/
├── reference/
├── standard/
├── idle/
├── walk/
├── crouch_idle/
├── crouch_walk/
├── hit/
├── death/
└── throw/              # M2 才生产
```

命名格式：

```text
character_xiaodong_<state>_<frame:02d>_v01.png
```

示例：

```text
character_xiaodong_walk_03_v01.png
character_xiaodong_death_05_v01.png
```

不提交 Sprite Sheet；Godot 使用独立 PNG 建立 `SpriteFrames`。

## 6. Godot 节点与导入约定

```text
XiaodongDaren (CharacterBody2D)
├── BodySprite (AnimatedSprite2D)
├── WeaponPivot (Node2D)
│   ├── WeaponSprite (Sprite2D)
│   └── MuzzlePoint (Marker2D)
├── ThrowablePoint (Marker2D)
├── CollisionShape2D
└── AnimationPlayer
```

要求：

- 人物、武器、投掷物、枪口火焰和弹壳永远是独立节点；
- `BodySprite` 的全部帧使用相同画布与 `feet_center`；
- 左右朝向优先 `flip_h`，只有镜像导致明显错误时才新增方向帧；
- Godot 导入关闭 Filter 和 Mipmaps，使用 nearest-neighbor；
- 角色碰撞不得跟随头发或手臂逐帧变化；
- 受击位移、击退和死亡禁用由状态机控制，不烘焙进图片位移。

## 7. Godot MCP 使用规则

Godot MCP 是编辑器交互的默认执行路径，但不是运行时依赖，也不能替代命令行与 CI。

### 7.1 必须优先使用 Godot MCP 的任务

- 打开并确认项目使用正确 Godot 版本；
- 检查和编辑场景树、节点类型、资源绑定与 SpriteFrames；
- 运行/停止项目并读取编辑器错误；
- 打开 `AssetGallery` 对比动画、锚点和镜像；
- 保存场景并确认没有丢失外部资源引用；
- 采集人工验收截图或记录。

### 7.2 仍必须使用 CLI 的任务

```bash
godot --headless --path . --editor --quit
godot --headless --path . res://tests/test_runner.tscn
```

CLI 用于解析、导入、自动测试和 CI 对齐。MCP 显示“能运行”不能代替无头测试通过。

### 7.3 MCP 不可用时

- 先记录 MCP server 名称、连接错误和已尝试动作；
- 能由 CLI 完整验证的纯代码任务可以继续；
- 涉及场景树、SpriteFrames、导入设置或视觉验收的任务必须标记 `BLOCKED`，不得猜测完成；
- 不把某个第三方 Godot MCP 实现写入游戏运行依赖。

## 8. `/goal` 阶段推进协议

Codex 每次 `/goal` 最多跨越一个里程碑边界。

执行顺序：

1. 阅读 `CODEX_START.md`、本文件和 `docs/status/CURRENT_STAGE.md`；
2. 检查 Godot MCP 连接；
3. 运行当前阶段自动测试；
4. 使用 Godot MCP 完成可观察验收；
5. 对照当前阶段全部强制门槛；
6. 任一门槛未通过：修复当前阶段，不改阶段编号；
7. 全部门槛通过：把 `CURRENT_STAGE.md` 更新为 `PASSED`，记录命令、构建、提交和证据；
8. 将下一阶段改为 `ACTIVE`；
9. 只开始下一阶段的第一个单闭环工作包；
10. 不得在同一次 `/goal` 中继续跨越第二个阶段。

自动测试通过但 Windows 10 分钟手动验收未完成时，当前阶段仍是 `ACTIVE_VALIDATION`，不能自动晋级。

## 9. 当前阶段到下一阶段

当前权威状态为 M1 灰盒战斗玩具 `ACTIVE_VALIDATION`。仓库已经具备 AK 射击玩具及自动测试基础，但仍需在目标 Windows 环境完成手感和性能门槛。

M1 全部通过后进入 M2。M2 第一个工作包固定为：

> 实现 `RunState` 与五波流程骨架的纯状态转换测试，只覆盖 `PREPARE → ACTIVE → CLEANUP → SETTLEMENT`，不同时实现商店、升级、三类敌人和正式 UI。

该工作包必须先写失败测试，再实现最小状态机，再通过 Godot MCP 打开测试场景确认无运行错误。
