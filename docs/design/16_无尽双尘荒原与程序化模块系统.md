# 16｜无尽双尘荒原与程序化模块系统

> 状态：第一版实现规范  
> 目标场景：`infinite_double_dust`  
> 依赖：`00_产品宪法.md`、`06_怪物与波次设计.md`、`09_Godot技术架构.md`、`14_像素美术Style_Bible.md`、`15_竞技场与刷怪空间系统.md`

> **主线裁决（2026-07-31）**：无限 Chunk 双尘荒原是当前默认产品路线和默认入口；固定竞技场只保留为 M0 回归场景与未来模式参考。

---

## 1. 设计结论

第一版地图从固定竞技场调整为“视觉与游玩上无限延伸”的沙漠旧城战场，但不创建真正无限大的单一场景。

运行时只维护玩家附近的有限 Chunk：

```text
无限世界坐标
+ 5×5 活跃 Chunk
+ 固定 Seed 的确定性模块
+ 稀疏 POI
+ 玩家周围屏幕外动态刷怪
+ 过远 Chunk、敌人和临时对象回收
```

核心开发顺序保持不变：

1. 先实现“无限移动且不出 Bug”；
2. 再实现“固定 Seed 的随机战斗模块”；
3. 再实现“有探索价值的 POI 与战斗导演”；
4. 灰盒验证通过后，才替换正式像素 Tile、墙体、木箱和环境组件。

第一版禁止直接使用完整 WFC、随机迷宫或复杂生态插件控制核心战斗空间。

---

## 2. 产品目标

玩家进入一片没有可见边界的黄沙旧城区域。移动时，前方不断出现新的战斗空间；回到旧坐标时，同一局内看到的模块布局保持一致。

地图必须持续提供以下通用射击空间语言：

- 黄沙、硬土地和旧城材质；
- 木箱、石墙、废车和路障；
- 长射线通道；
- L 形转角；
- 开阔广场；
- 狭窄侧路；
- 双箱掩体；
- 废弃补给站。

这些元素只能提取通用战术语汇，不复制任何现有商业地图的雷达轮廓、点位名称、贴图、标记、建筑比例或具体物件排列。

---

## 3. 第一版范围

### 3.1 必须实现

- 玩家可跨越原 M0 边界持续移动；
- 世界按 Chunk 流式加载和卸载；
- 相同世界 Seed 与 Chunk 坐标生成相同模块；
- 每帧限制 Chunk 构建数量；
- 前进方向优先生成；
- 六种普通战斗模块；
- 一个稀疏 POI：废弃补给站；
- 敌人在玩家屏幕外的环形区域生成；
- 敌人与 Chunk 超出回收距离后进入对象池或释放；
- 原 M0 AK 射击、后坐力、弹匣和换弹回归测试继续通过；
- 新场景可以被 Godot 无头模式解析和实例化。

### 3.2 暂不实现

- 正式像素 TileSet；
- 完整城镇或地下空间；
- 可破坏建筑；
- 高低差和跳跃；
- 多生态群系；
- 完整 20 波和商店；
- 世界永久存档；
- WFC、Gaea 或第三方无限地形插件的运行时依赖；
- 对所有历史 Chunk 保存敌人、弹壳和掉落物状态。

## 4. 世界与 Chunk 参数

第一版基准参数：

| 参数 | 值 |
|---|---:|
| Chunk 实际尺寸 | `1024×1024 px` |
| 活跃半径 | `2` |
| 理论活跃数量 | `5×5 = 25` |
| 单帧最大构建数 | `1` |
| 世界 Seed | `424242` |
| 普通敌人最小生成距离 | `850 px` |
| 普通敌人最大生成距离 | `1250 px` |
| 敌人回收距离 | `2100 px` |
| 第一版最大活动敌人数 | `24` |
| 预热对象池 | `8` |

Chunk 坐标计算必须使用向下取整，保证负坐标正确：

```text
chunk_x = floor(world_x / chunk_size)
chunk_y = floor(world_y / chunk_size)
```

例如 `world_x = -1` 时必须属于 Chunk `-1`，不能错误落入 Chunk `0`。

## 5. 固定 Seed 合同

地形生成不得依赖全局随机流。每个 Chunk 使用以下输入生成自己的描述：

```text
world_seed + chunk_coord.x + chunk_coord.y
→ chunk_seed
→ module_id
→ rotation_quarters
→ poi_id
→ decoration_seed
```

必须满足：

```text
同一 world_seed + 同一 chunk_coord
= 相同 module_id、旋转、POI 和装饰 Seed
```

敌人生成使用单独的随机子流，不得消费地图生成随机数。武器散布继续使用自己的 `DeterministicSpread` 子流。

这样可以保证：

- 地图卸载后重新进入仍可复现；
- 修改敌人数量不会改变地形；
- 修改武器射击不会改变 POI；
- 自动测试可以锁定典型坐标的结果。

## 6. 战斗模块语法

第一版使用“人工定义模块 + 程序选择与旋转”，不随机逐格生成墙体。

### 6.1 普通模块

| `module_id` | 作用 |
|---|---|
| `open_square` | 中央开阔，角落提供小型掩体，适合基础走位 |
| `long_lane` | 两条平行墙形成长射线通道，旋转后支持横向或纵向 |
| `l_corner` | L 形石墙切割视野，强化转角、手雷与近距离遭遇 |
| `double_crate` | 双箱之间形成可绕行掩体和短暂停枪位置 |
| `narrow_side` | 一侧宽、一侧窄，制造风险不同的两条路线 |
| `wreck_cover` | 废车和路障形成不规则中型掩体 |

### 6.2 稀疏 POI

第一版仅实现：

| `poi_id` | 平均密度 | 功能 |
|---|---:|---|
| `supply_outpost` | 约每 12～13 个 Chunk 一个 | 明显地标、后续补给和事件挂点 |

第一阶段 POI 只提供视觉与空间结构，不直接给予经济奖励，以免地图底座和奖励系统同时耦合。

### 6.3 接口预留

模块描述保留：

- `module_id`；
- `rotation_quarters`；
- `poi_id`；
- `chunk_seed`；
- `decoration_seed`。

后续加入 Tiled/YATI 时，`module_id` 可映射到人工制作的 `.tmx` 或 `.tscn`，不改变 Chunk 管理器接口。

## 7. Chunk 流送规则

`InfiniteChunkManager` 只负责世界生命周期，不负责波次和敌人组成。

流程：

1. 计算玩家当前 Chunk；
2. 生成半径 `2` 内的期望坐标；
3. 删除已经离开期望集合的 Chunk；
4. 找出缺失坐标；
5. 按“距离优先 + 移动方向加权”排序；
6. 每帧最多创建一个 Chunk；
7. Chunk 创建时通过 `DesertChunkLayout.describe()`获取确定性描述；
8. Chunk 发出加载遥测信号。

加载优先级要求：

- 玩家所在 Chunk 第一；
- 距离较近的 Chunk 优先；
- 距离相同，玩家移动方向前方优先；
- 玩家静止时使用稳定坐标顺序，避免每帧重排抖动。

回收要求：

- 活跃 Chunk 数不得随移动时间持续增长；
- Chunk 删除前必须移除其碰撞体；
- 已离开加载集合的排队项必须取消；
- 不允许同一坐标重复创建两个实例。

## 8. 灰盒 Chunk 表现

第一版 Chunk 使用程序绘制的灰盒，不等待正式像素素材：

- 基础黄沙矩形；
- 少量由 `decoration_seed` 决定的深浅沙斑和碎石；
- 木箱、石墙、废车使用不同灰盒颜色；
- 障碍物拥有 Terrain 碰撞层；
- 玩家碰撞掩码包含 Terrain；
- 无限场景中的武器射线同时检测敌人和 Terrain。

障碍物不能覆盖 Chunk 四边的全部通行面。任何模块都必须保留至少两条明显撤离方向。

正式美术阶段再将这些灰盒矩形替换为：

- 沙地 Tile；
- 墙体直段、内角、外角和破损段；
- 木箱、石箱和双箱组合；
- 废车、路障和沙袋；
- 补给站组件；
- 车辙、弹坑、裂纹和碎石 Decal。

---

## 9. 动态刷怪与回收

无限地图没有固定边缘，因此 `InfiniteSpawnDirector` 使用以玩家为中心的环形候选区。

候选点必须满足：

- 距离玩家在 `850～1250 px`；
- 当前候选点所在 Chunk 已加载；
- 候选点不在 Terrain 碰撞内部；
- 候选点不在玩家当前可见区域内；
- 无合法候选点时延后生成，禁止贴脸补偿。

第一版敌人是用于验证地图和回收链路的追击灰盒：

- 可被 AK 射线命中；
- 追向玩家；
- 与 Terrain 发生碰撞；
- 被击杀或距离玩家超过 `2100 px` 后回收到对象池；
- 不实现玩家生命和接触伤害。

敌人组成和波次预算仍属于后续 `WaveDirector`，不得写死在 Chunk 内。

## 10. 场景与代码边界

推荐结构：

```text
scenes/run/infinite_desert_prototype.tscn
├── InfiniteDesertRunRoot
├── ChunkManager
├── SpawnDirector
├── Player
│   ├── Camera2D
│   └── WeaponController
├── Presentation
└── HUD
```

代码职责：

| 文件 | 职责 |
|---|---|
| `src/world/desert_chunk_layout.gd` | 坐标到确定性模块描述的纯逻辑 |
| `src/world/chunk_stream_planner.gd` | 期望坐标、加载顺序和回收列表的纯逻辑 |
| `src/arena/infinite_desert_chunk.gd` | 单个 Chunk 的灰盒绘制与碰撞体 |
| `src/world/infinite_chunk_manager.gd` | Chunk 生命周期、加载队列和遥测 |
| `src/spawn/spawn_ring_sampler.gd` | 固定 Seed 的环形候选点采样 |
| `src/spawn/infinite_spawn_director.gd` | 候选过滤、生成节奏、活动敌人与对象池 |
| `src/actors/prototype_chaser.gd` | 可回收的第一版追击敌人 |
| `src/run/infinite_desert_run_root.gd` | 连接射击反馈、HUD 和世界系统 |

禁止：

- 在 Chunk 脚本中决定波次；
- 在敌人脚本中加载/卸载 Chunk；
- 在地图随机流中生成武器散布；
- 在 `SpawnDirector` 中根据具体 `module_id` 写大量特殊分支。

## 11. 开源库策略

第一版核心不直接依赖外部地图生成库。

原因：

- 当前需求是有限且可测试的 Chunk 流送；
- 战斗空间必须人工可控；
- 插件升级不应控制项目核心生命周期；
- 现有 M0 使用纯 GDScript，保持依赖最少更容易验证。

后续可选：

- **YATI**：当人工模块达到约 20 个后，用 Tiled 批量编辑和导入；
- **Gaea**：用于离线或编辑器内生成地表遮罩与装饰分布；
- **WFC**：仅用于模块内部视觉衔接或城镇废墟填充，不承担战斗结构；
- **gdUnit4**：当测试规模超过现有轻量测试运行器承载范围时再评估迁移。

## 12. 测试合同

### 12.1 确定性

- 同 Seed、同坐标重复调用结果完全一致；
- 负坐标可复现；
- 多个坐标能产生不止一种模块；
- POI 密度保持稀疏且可复现。

### 12.2 流送

- 半径 `2` 正好产生 25 个期望坐标；
- 当前坐标一定包含在集合中；
- 负世界坐标向下映射；
- 当前 Chunk 已激活时，移动方向前方候选优先；
- 离开范围的坐标进入回收列表。

### 12.3 环形刷怪

- 相同 Seed 和采样序号得到相同位置；
- 所有候选距离位于最小值和最大值之间；
- 不同采样序号产生不同候选。

### 12.4 场景集成

- 无限场景可加载；
- 包含玩家、Camera2D、ChunkManager、SpawnDirector、WeaponController 和 HUD；
- 无限场景玩家关闭固定竞技场边界限制；
- 原 M0 场景仍可加载。

## 13. 性能与遥测

第一版调试时至少记录：

- 当前 Chunk 坐标；
- 活跃 Chunk 数；
- 待加载队列长度；
- 本次加载/卸载坐标；
- 活动敌人数；
- 对象池数量；
- 无合法生成点的延后次数。

验收目标：

- 连续沿单一方向移动 10 分钟，活跃 Chunk 数不持续增长；
- 不出现可见地图空洞超过正常单帧构建延迟；
- 同一坐标不重复加载；
- 相同 Seed 重开后典型坐标模块一致；
- 敌人数受上限控制；
- 过远敌人能回收；
- 现有射击回归测试全部通过。
